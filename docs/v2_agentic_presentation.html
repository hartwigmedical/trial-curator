Act 1 · the problem

From free text to a structured, matchable resource

The key sections of each trial arrive as free text. We transform them into a structured resource file with controlled vocabulary for the downstream matching engine.

Section 1

Basic details

Recruitment status, phase, sponsor, locations — the basic info fields, carried through deterministically.

Section 2

Eligibility

Who qualifies — cancer type, gene alterations, biomarkers, prior therapy — as structured logic in controlled vocabulary (OncoTree, finding-model syntax).

Section 3

Drug utility

The interventional drugs — canonical identity, class, targets, and TGA / PBS approval status.

Act 1 · what came before

Where the old pydantic curator fell short

The v1 curator got us started, but four problems it couldn't adequately solve are exactly what motivated the rewrite.

Problem 1

No automated verification

A linear chain of one-shot LLM calls — requires a human reviewer. Virtually impossible to manually detect all errors across ~2,000 trials.

Problem 2

No multiple eligibility criteria combinations

E.g. cancer type and gene alterations are treated as independent criteria. Could not handle cancer × gene combinations in more complex trials/cohorts without manual overwriting.

Problem 3

No external web search capability for drug enrichment

Drug annotations — drug class, target–mechanism, and TGA / PBS status — can't be filled from the protocol text alone.

Problem 4

Heavy reliance on post-processing manual correction and handcrafted mapping files

No reliable means of transforming input text into our controlled vocabulary without manually created mapping files.

Act 2 · the chosen solution

An evaluator–optimizer loop — a doer and its reviewers

A doer generates the answer; one or more reviewer agents evaluate it against the source; if a reviewer flags a problem, its critique feeds back and the doer re-generates.

✗ a reviewer flags a problem  →  back to the doer · re-generate (≤ 6 attempts)
doer

Reads the source, emits the whole candidate in one pass — a DNF table, a drug record, a mapping.

→candidate
reviewer panel

Several focused agents, each judging one dimension, in parallel → verdict + problems.

→verdict
decision

✓ all clear → done.
✗ a problem → loop back.

↺ On a problem, the loop returns to the doer to re-generate (≤ 6 attempts).
Why a panel — not a single reviewer agent

When a stage has several independent things to check, the review fans out: each focused agent verifies one dimension, in parallel. A narrow, single-dimension check is easier and more reliable than one agent judging everything at once — the same generation/verification asymmetry, applied to the reviewer itself. Extraction runs a 5-agent panel; simpler stages (mapping, drug) need only one reviewer.

Act 2 · why it works

Generation is a search problem. Verification is checking a certificate.

Doer · solves

Construct a faithful DNF

Across 5 columns × cohorts × provenance × inline negation, jointly. Combinatorial; its natural failure mode is over-enumeration — multiplying a boolean expression out and losing which ORs are independent axes vs. mutually-exclusive alternatives.

Reviewer · checks

Is this dimension faithful?

Given the finished table and the source, judge one axis. A far cheaper task — a lower complexity class. Like NP: a solution is verifiable in P even when finding it isn't. (The same reason peer review works: writing the proof ≫ checking it.)

verification < generation — but only with an adversarial, fresh-pass, independent checker that can see the whole certificate.
Act 2 · key features

Six features that make the workflow work

Orchestration

Deterministic scaffold

Plain Python owns control flow — parallelism, the loop, durable saves, the join. The LLM never orchestrates.

The engine

Doer → reviewer loop

One shared refine harness across extraction, mapping and drug — generate, evaluate, refine.

Correctness invariant

Reviewer only advises

The reviewer returns verdict + problems, never a rewrite; the doer is the sole writer.

Decomposition

One agent per task

Split only genuinely independent work; whole DNF rows stay in one doer; independent checks fan out.

Speed & determinism

Content-addressed cache

Identical request → identical stored output, no API call. Reproducible, near-instant re-runs, no cost on hits.

Output

3NF on a shared key

Relational tables joined on trial_arm_id; a flat combined.tsv for the matcher.

Act 3 · learning · the reviewer's vantage point

SIOPEN NCT04221035 — a real over-enumeration

The source states one gene criterion: MYCN amplification OR focal MYC OR MYCL amplification — three alternatives; a patient needs one.

What the doer produced 9 gene values, including 6 spurious AND-pairs like MYCN amp AND focal MYCL amp — and both orderings of each. 84 / 218 rows (38%) carried a fabricated conjunction.
Why nothing caught it It's satisfiable (a patient could have two amplifications) — so the deterministic validator can't flag it. Only comparison to the source reveals it. The reviewer panel missed it too — every reviewer judged cells, none saw the deduplicated set vs. the source's true alternative count.
The fix — architectural, not a prompt Add a reviewer with the aggregate vantage point: it sees the whole distributed DNF and counts alternatives-vs-source. Plus a deterministic commutative-duplicate dedup (A AND B == B AND A).

Same lesson, two more cases Cohort cross-product blow-up 680→32 rows (587 impossible → 0); prior-therapy subsuming twins 108→47. All are whole-output properties a forward generator can't see in itself.
Act 3 · the contract in practice

The reviewer only advises. The doer is the sole writer.

doer · generates / re-generates

The only thing that ever writes a value. On a failure it gets its own prior table + only the flagged issues, and keeps unflagged rows verbatim (incremental repair — preserves correct work, aids convergence).

▼ candidate
reviewer · verdict + problems only

ReviewVerdict has no output field. It critiques; it never rewrites. Every check — deterministic validators and the LLM reviewer — returns only faithful? + problems.

↺
Refine — feed the critique back; the doer re-generates. Bounded (≤ 6 attempts), returns the best attempt, stops early on convergence or an exact-repeat cycle.
Why one writer Every accepted value was re-checked after it was written, and no unchecked edit can reach the output. It's Reflexion, not an editor.
Honest trade-off It pays full re-generation on every fail, and can stall convergence on the hardest trials. We accept that for the correctness guarantee.
Act 3 · the eligibility path

Verbatim → DNF → map → reconcile

  • Verbatim first. Extract the criteria quoted, tagged with the section they came from — the audit anchor a human can check against the protocol.
  • Interpret to DNF. Rows are ORed, cells are ANDed, exclusions inline as NOT(). One row = one satisfiable (trial, arm) conjunction — self-contained for the matcher.
  • Map each cell to a controlled representation (OncoTree, finding-model).
  • Reconcile across the whole run so semantically-equivalent inputs never get different codes.
A DNF row, concretely
[C1] cancer_type = "ES-SCLC AND NOT(complex SCLC)"
[C1] molecular_biomarker = "HR+ AND HER2-"
[trial-wide] prior_therapy = NOT(prior anti-PD-1)
Why DNF (not a boolean tree) The downstream matcher wants flat, self-contained rows it can test one at a time — not an arbitrary AND/OR/NOT/IF expression tree to interpret. DNF is the contract.
Act 3 · the drug path & trust boundaries

Researched once per drug — and the exact facts never touch the model

Stage 1 · identity

Canonicalize

Brand / code → INN; a regimen splits into components. rxcui resolved by lookup.

Stage 2 · enrichment

Annotate

Modality, (target, action) pairs, class. POTTR class + ATC by deterministic lookup.

Stage 3 · regulatory

Approvals

TGA / PBS per indication via web search on official sources, each with an evidence link.

Trust boundary — the LLM supplies judgement and language; code supplies identity. rxcui / ATC / POTTR class are lookups, never guesses; the reviewer judges plausibility from its own knowledge, it does not re-search. And each distinct drug is researched once (~2,400 raw → 1,275 canonicals).
Act 3 · the data model

3NF relational tables on one shared join key

Arm identity is a first-class shared thing, not embedded per path. Both paths write arms to one central trial_arms registry and link to it by a deterministic slug.

The join key

trial_arm_id = {trialId}::{arm}

A deterministic slug, chosen over an auto-increment surrogate: reproducible with no sequence authority → safe for parallel workers, idempotent on re-runs, and human-readable.

The shape Eligibility = 2 content tables + 3 map tables. Drug = 5 tables. One shared arm registry. Denormalized combined.tsv is materialized for the matcher.
  • Identity separated from enrichment — “which drug is this?” is a different table from “what is this drug?”
  • No drug facts in the eligibility store — drugs join in by trial_arm_id.
  • Each stage checkpoints per trial — a crash loses only in-flight items.
  • One axis to query — (target, action) pairs, OncoTree codes, finding-model, TGA/PBS all hang off the same key.
Act 3 · determinism

You can't pin the temperature. So make the system deterministic.

gpt-5.x won't even accept temperature or seed — we can't constrain the model's sampling. So determinism lives one layer out: a content-addressed response cache that memoizes at the request boundary.

How it works

Key = sha256({model, instructions, input, schema}). Hit → return the stored response, no API call. Miss → call the model, then store. Identical request ⇒ identical output — reproducibility without touching the sampler.

Three wins, one mechanism

Determinism (re-runs are byte-stable) · speed (a re-run is near-instant — 9/10 complex trials re-ran in ~1s) · cost (a hit spends nothing, including the expensive web search).

Correctness under change — prune by prompt provenance Each entry stores its agent's prompt_sha. Change a prompt and its fingerprint changes — stale entries are garbage-collected automatically, so a re-run recomputes exactly what the edit affected and nothing else.
Act 3 · how prompts are built

Prompts are developed like ML models — train / validate / test

Hand-curated answer sets are held out as verification data, not ingested into the prompt. A prompt carries grammar/ontology + ~8–12 examples; the curated spreadsheets grade it.

1 · train

Live-test & self-review

Run a trial sample, read every output, find the failure patterns.

2 · fix

Principle-level only

A rule + ≤1 example — never a per-case patch. If it can't be stated as a principle, it doesn't go in.

3 · validate

On a disjoint sample

A larger, non-overlapping set confirms the fix generalised — guarding against overfitting the prompt.

Where it's honest about falling short

219 / 1,999
trials finish faithful=False — best-effort on hard multi-cohort trials; the extractor exhausts its 6-attempt budget. Output is still written & logged, never silently dropped.
  • Convergence tail — deep sub-cohort trials return best-of-6; a “patience” early-stop would trim the waste.
  • cancer_type purity — occasionally ANDs a same-type refinement the 5-column schema has no home for.
