Act 1 · the problem

From free text to a structured, matchable resource

The key sections of each trial arrive as free text. We transform them into a structured resource file with controlled vocabulary for the downstream matching engine. It has three sections.

Section 1

Basic details

Recruitment status, phase, sponsor, locations — the basic info fields, carried through deterministically.

Section 2

Eligibility

Who qualifies — cancer type, gene alterations, biomarkers, prior therapy — as structured logic in controlled vocabulary (OncoTree, finding-model syntax).

Section 3

Drug utility

The interventional drugs — canonical identity, class, targets, and TGA / PBS approval status.

Act 1 · what came before

Where the old pydantic curator fell short

The v1 curator got us started, but five problems it couldn't adequately solve are exactly what motivated the rewrite.

Problem 1

No automated verification

A linear chain of one-shot LLM calls — requires a human reviewer. Virtually impossible to manually detect all errors across ~2,000 trials.

Problem 2

No multiple eligibility criteria combinations

E.g. cancer type and gene alterations are treated as independent criteria. Could not handle cancer × gene combinations in more complex trials/cohorts without manual overwriting.

Problem 3

No external web search capability for drug enrichment

Drug annotations — drug class, target–mechanism, and TGA / PBS status — can't be filled from the protocol text alone.

Problem 4

Heavy reliance on post-processing manual correction and handcrafted mapping files

No reliable means of transforming input text into our controlled vocabulary without manually created mapping files.

Problem 5

Read only the eligibility section

Eligibility-relevant detail also appears in the title, description, conditions, and arm text — v1 read only the eligibility criteria and missed it.

Act 2 · the chosen solution

An evaluator–optimizer loop — a doer and its reviewers

A doer generates the answer; one or more reviewer agents evaluate it against the source; if a reviewer flags a problem, its critique feeds back and the doer re-generates.

✗ a reviewer flags a problem  →  back to the doer
doer

Reads the source, emits the whole candidate in one pass — a DNF table, a drug record, a mapping.

→candidate
reviewer panel

Several focused agents, each judging one dimension, in parallel → verdict + problems.

→verdict
decision

✓ all clear → done.
✗ a problem → loop back.

↺ On a problem, the loop returns to the doer to re-generate.
Why a panel — not a single reviewer agent

When a stage has several independent things to check, the review fans out: each focused agent verifies one dimension, in parallel. A narrow, single-dimension check is easier and more reliable than one agent judging everything at once. Extraction runs a 5-agent panel; simpler stages (mapping, drug) need only one reviewer.

cancer typemolecularstructureprior therapydrug
the feedback that drives convergence On a re-run the doer gets its original instructions + its own prior attempt + the reviewer's critique (only the flagged issues; passing rows are kept). So its effective prompt becomes specific to this trial with each retry.
blocking vs advisory Most reviewers are blocking — a flagged problem sends the work back. A few are advisory (e.g. the drug check): they annotate, but don't trigger a re-generation.
Act 2 · why it works

Why the loop works: verification < generation

The two roles aren't equally hard. Producing a faithful answer is a search problem; checking a proposed one is closer to a look-up. That asymmetry is what the loop exploits.

the doer — the hard part

Construct the answer

Build it from scratch — a faithful DNF, a canonical drug, a mapping. Combinatorial, with many ways to go wrong.

the reviewer — the easy part

Check the answer

Given a finished answer and the source, judge one dimension — a direct comparison. Cheaper, and more reliable.

what “verification < generation” means Producing the right answer from scratch is hard; checking whether a proposed one is right is much easier — it takes less work, and less capability. Think of a mathematical proof: finding it can take years; checking a written proof is a careful read-through. So we spend our strongest effort on the doer, and use cheaper, focused reviewers to catch its mistakes — and we can afford several of them.
verification < generation — but the payoff only lands if the checker is independent, sees the whole answer, and is actively looking for faults.

Act 2 · key features

Key features

The doer→reviewer loop is the engine (previous slide). These are the engineering choices that make it reliable, cheap, and queryable — the last four are expanded over the next four slides.

Orchestration

Deterministic scaffold

Plain Python owns control flow — parallelism, the loop, durable saves, the join. The LLM never orchestrates.

Decomposition

One agent per independent task

The number of agents follows one rule: split only genuinely independent work. Co-dependent outputs stay in one agent; independent checks fan out.

Agent contract

Reviewer advises, doer writes

The reviewer returns a verdict + problems, never a rewrite; the doer is the sole writer.

Trust boundaries

Exact facts by lookup, not LLM

Drug ids, codes and classes come from deterministic lookups — never a model guess.

Output

3NF relational model

Each fact stored once, joined on a shared key — no duplication, clean joins, reuse.

Speed & determinism

Content-addressed cache

Identical request → identical stored output, no API call — our equivalent of temperature 0.

Act 2 · the agent contract

The reviewer advises; the doer writes

doer · the sole writer

The only agent that ever writes a value. On a failure it re-generates from its own prior attempt + the flagged issues, keeping the rows that already passed.

▼ candidate
reviewer · verdict + problems only

ReviewVerdict carries no output field — it can flag a problem but cannot rewrite the answer. So every value that reaches the output was written by the doer and then re-checked.

bounded The loop runs up to 6 attempts, stopping early once the reviewers are satisfied — or once the same problems repeat (no point looping).
last resort — the reviewer supplies a fix If the doer stays stuck, the loop escalates: the reviewer is asked for a concrete, complete fix (not just problems), which the doer applies. The one time the reviewer offers a solution — and the output is still written, never dropped.
Act 2 · trust boundaries

What we don't ask the model

The model supplies judgement and language; deterministic code supplies the exact, checkable facts. Each side does what it's reliable at.

Deterministic lookup — never a guess

Facts with one correct value, taken from a reference:

  • a drug's rxcui and ATC code (RxNorm)
  • its POTTR drug class
  • OncoTree & finding-model syntax (validators)

The web search gives the drug's name; resolve_rxcui(name) gives its id — a wrong id would poison every join.

LLM judgement & language

Calls that need reading and interpretation:

  • which drug is investigational vs auxiliary
  • how to phrase an indication
  • whether a mapping is faithful to the source

The reviewer judges from its own knowledge — it does not re-search.

Because a drug's facts depend on the drug, not the trial, each distinct drug is researched once (~2,400 raw names → 1,275 canonicals) and reused everywhere thereafter.

Act 2 · the data model

3NF relational tables on one shared key

Third normal form: every fact lives in exactly one place, and rows reference each other by keys. Arm identity is the shared spine both paths join on.

the shared key

trial_arm_id = {trialId}::{arm}

A deterministic id derived from the trial and its arm — reproducible with no central counter, so parallel workers and re-runs always agree, and it stays human-readable.

the shape Eligibility: 2 content tables + 3 mapping tables. Drug: 6 tables (incl. the new per-arm trial_arm_drug_role). One shared arm registry. The flat combined.tsv is materialized from these for the matcher.
why 3NF
  • No duplication — a drug's mechanism or approval is stored once, not copied into every trial that uses it.
  • Update in one place — correct a fact once and every reference sees it.
  • Integrity by keys — joins can't silently mismatch; a referential check catches orphans.
  • Reuse — the same drug annotation serves every arm that uses that drug.
Act 2 · determinism, speed & cost

One cache, three wins

We re-run the pipeline constantly — iterating prompts, resuming interrupted runs. Every LLM call is served through a content-addressed cache: the key is a hash of the exact request (model + instructions + input + schema); a hit returns the stored response with no API call. That buys three things:

win 1

Determinism

Identical request ⇒ identical output — byte-stable re-runs. Our equivalent of temperature 0, at the system level.

win 2

Speed

Re-running already-seen work is near-instant — 9 of 10 complex trials re-ran in ~1 second.

win 3

Cost

A cache hit spends nothing — including the expensive web search on the drug side.

staying correct when a prompt changes Each entry records the prompt it came from. Change a prompt and its fingerprint changes — stale entries are dropped automatically, so a re-run recomputes exactly what the edit affected and reuses everything else.

Deep dive · a bug we caught

Over-enumeration — the doer fabricating combinations

The source (NCT04221035, SIOPEN) states one gene criterion: MYCN amplification OR focal MYC OR MYCL amplification — three alternatives; a patient needs one.

what went wrong The doer expanded those alternatives into spurious AND-combinations (e.g. MYCN amp AND focal MYCL amp) — 84 of 218 rows carried a fabricated conjunction.
why nothing caught it Each pair is individually satisfiable (a patient could have both), so the validator passed it and every single-cell reviewer accepted it. And the doer emits rows one at a time, never seeing its own finished table — so it can't notice the explosion either.
the fix — two parts (1) a new reviewer that sees the whole de-duplicated table (not one cell): it counts how many alternatives the source states for each criterion — here, 3 — and flags any output enumerating more combinations than that as fabricated ANDs. (2) a deterministic pass that drops rows which are merely reorderings of each other (A AND B = B AND A).
218
rows before — fabricated
45
rows after — faithful
the lesson The panel is only as good as its lenses: a whole-output error needs a whole-output reviewer.

Act 3 · limitations

Where the evaluator–optimizer struggles

convergence isn't guaranteed

Hard inputs don't fully resolve

On deeply nested, multi-cohort trials (e.g. a 6-cohort brainstem-glioma protocol), the doer can't satisfy every reviewer within the attempt budget. 219 of 1,999 trials returned a best-effort answer rather than a fully converged one.

correctness costs compute

Full re-generation on every fail

The writer-only contract means the doer rebuilds its answer each round rather than editing in place — more tokens and latency than a patch. The price of a re-checked output.

the reviewer's blind spots

It only catches what it's told to

A dimension no reviewer is looking at can slip through — the panel is only as good as its lenses. (An over-enumeration bug lived here until we added an aggregate-view reviewer.)
