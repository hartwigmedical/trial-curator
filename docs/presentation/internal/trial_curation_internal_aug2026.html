Act 1 · the problem

From free text to a structured, matchable resource

The key sections of each trial arrive as free text. We transform them into a structured resource file with controlled vocabulary for the downstream matching engine. It has three sections.

Section 1

Basic details

Recruitment status, phase, sponsor, locations — the basic info fields, carried through deterministically.

Section 2

Eligibility

Who qualifies — cancer type, gene alterations, biomarkers, prior therapy — as structured logic in controlled vocabulary (OncoTree, finding-model syntax).

Section 3

Drug utility

The interventional drugs — canonical identity, class, targets, and TGA / PBS approval status.

Act 1 · the problem

Why this is difficult, and where version 1 fell short

Eligibility criteria are written for human readers. The structure a matching engine needs is present in the text but not marked, and has to be recovered before any value can be mapped to vocabulary.

Four recurring difficulties
  • Alternatives are not delimited. “with MYCN amplification, or focal high level MYC or MYCL amplification” NCT04221035 states three alternatives, of which a patient needs one. Nothing marks where one ends.
  • Requirements combine. A cancer type, an alteration and a prior-therapy condition apply together, and different arms of the same trial combine them differently.
  • Exclusions have a scope. An exclusion may apply to the whole trial or to one arm of it. Applying an arm-scoped exclusion trial-wide would exclude eligible patients.
  • Terminology varies. Across the universe there are 4,979 distinct ways of writing a cancer type, and each has to resolve to the correct code.
Five problems that motivated the rewrite

Version 1 was a linear chain of one-shot LLM calls over the eligibility section, corrected manually afterwards.

  • No automated verification. A linear chain of one-shot calls requires a human reviewer. Virtually impossible to manually detect all errors across ~2,000 trials.
  • No combinations of eligibility criteria. Cancer type and gene alterations were treated as independent, so cancer × gene combinations needed manual overwriting.
  • No external web search for drug enrichment. Drug class, target–mechanism and TGA / PBS status cannot be filled from the protocol text alone.
  • Reliance on handcrafted mapping files to reach our controlled vocabulary.
  • Read only the eligibility section — relevant detail also appears in the title, description, conditions and arm text.

Act 2 · the chosen solution

An evaluator–optimizer loop — a doer and its reviewers

A doer generates the answer; one or more reviewer agents evaluate it against the source; if a reviewer flags a problem, its critique feeds back and the doer re-generates.

✗ a reviewer flags a problem  →  back to the doer
doer

Reads the source, emits the whole candidate in one pass — a DNF table, a drug record, a mapping.

→candidate
reviewer panel

Several focused agents, each judging one dimension, in parallel → verdict + problems.

→verdict
decision

✓ all clear → done.
✗ a problem → loop back.

↺ On a problem, the loop returns to the doer to re-generate.
Why a panel, rather than a single reviewer agent

When a stage has several independent things to check, the review fans out: each focused agent verifies one dimension, in parallel. A narrow, single-dimension check is easier and more reliable than one agent judging everything at once. Extraction runs a 5-agent panel, plus a sixth reviewer that reads the assembled table; simpler stages (mapping, drug) need only one reviewer.

cancer typemolecularstructureprior therapydrugenumeration — the whole table
why checking beats writing Producing a correct answer is a search problem; checking a proposed one is closer to a look-up. Think of a mathematical proof: finding it can take years, while checking a written proof is a careful read. So the hard half is done once and the easy half is done repeatedly.
the feedback that drives convergence On a re-run the doer gets its original instructions + its own prior attempt + the reviewer's critique (only the flagged issues; passing rows are kept). So its effective prompt becomes specific to this trial with each retry. Most reviewers are blocking; the drug check is advisory.
Act 2 · trust boundaries

What code computes, and what an LLM must judge

Anything with one correct value that can be looked up is resolved by code, and is never asked of an LLM. The LLM supplies judgement and language.

Deterministic lookup — never a guess

Facts with one correct value, taken from a reference:

  • a drug's rxcui and ATC code (RxNorm)
  • its POTTR drug class
  • OncoTree and finding-model syntax (validators)
  • which arms a trial has, on CT.gov

The web search gives the drug's name; resolve_rxcui(name) gives its id — a wrong id would poison every join.

LLM judgement and language

Calls that need reading, interpretation or search:

  • which criteria belong to which arm
  • which drug is investigational and which is a backbone or comparator
  • which OncoTree node a phrase denotes
  • whether a value is faithful to the source

The reviewer judges from its own knowledge — it does not re-search.

Because a drug's facts depend on the drug rather than the trial, each distinct drug is researched once and reused everywhere thereafter: 2,546 distinct raw intervention strings resolve to 1,312 drugs.

Act 2 · verifying correctness

Two layers of checking: every value, and every cycle

Spot checks — each value, as it is produced

Every value is checked twice before it is stored: once for faithfulness by an LLM reviewer, once for form by code.

  • Does every quoted span really appear in the source
  • Is the cancer type the tumour under study, at the right level of detail
  • Is each molecular value in the right column, and the row structure and per-arm scope correct
  • Is the code valid and the alteration expression syntactically valid
  • Is anything self-contradictory — the same term required and excluded
  • Did the drug identifier, class and ATC code come from a lookup
Gates — the finished cycle, before it is trusted

Spot checks cannot detect a cycle that curated only half the universe and still produced a plausible-looking file. Twelve deterministic gates examine the finished state on disk — no LLM, no network.

  • fail every eligibility, drug and role row points at an arm that exists
  • fail every arm producing no eligibility carries a reason
  • fail a retired trial is gone from every table
  • fail after = before − retired + newly curated holds exactly, and reference data never shrank
  • fail no mapped value silently broadened or narrowed since the last cycle
  • warn an independent validator re-checks the finished file, and known accepted findings stay visible so a gate fails on new problems
the cycle of 6 August 2026 Verdict WARN: 10 gates PASS, 2 WARN, 0 FAIL. 620 distinct OncoTree expressions and 847 gene-alteration expressions carry 0 defects; 1,844 of 2,022 trials (91%) pass the independent validator cleanly; 5 known extraction misses are waived in code, in git, each naming its follow-up. Any FAIL exits non-zero so the scheduler sees it.

the OR doubles the rows “MTAP deletion or MTAP loss” is one criterion with two alternatives, and a patient needs one. Each alternative becomes its own row.
the exclusion splits the population The AGA exclusion applies to nonsquamous patients only. A rule that holds for part of a population cannot sit in a row that has to be satisfiable as a whole — so the histology is split, and the exclusion appears in the two nonsquamous rows. The same happens in each of the trial's six arms.
Stage 5 · controlled vocabulary

Each interpreted value is mapped once, in three stages

1 registry record→2 arms→ 3 quote→4 interpret→ 5 map→6 drugs→ 7 export
stage 1 · translate

LLM doer → reviewer

One value at a time, with the vocabulary and worked examples in the prompt. A value is a function of itself alone, so nothing it produces can churn a neighbouring value.

stage 2 · canonicalise

Deterministic, no LLM

Order the alternatives, remove duplicates, factor the negations, repair a leaked name into its code — so two spellings of one answer become one string.

stage 3 · finalise

The approved register

Reviewed corrections, held in code and in git. A difference between stage 2 and stage 3 is an approved override, and each one names the prompt weakness it stands in for.

the identifier comes from a lookup The web search supplies the name; RxNorm supplies the id. MK-4716 is investigational and has no RxCUI, so it is keyed by name — visibly, so the difference is never mistaken for a resolved identifier.

Where it still struggles, and where it is going

Limit 1

The hardest trials do not converge

On deeply nested, many-cohort protocols the doer cannot satisfy every reviewer within the round budget. In the full run of 25 July 2026, 219 of 1,999 trials (11%) ended on a best-effort answer.

Those outputs are written and marked for human review, rather than dropped.

Limit 2

Correctness costs compute

Because a reviewer may object but never edit, the doer rewrites the whole answer each round rather than patching it. This costs more tokens and more time than a targeted edit.

Limit 3

Reviewers only catch what they are asked

A mistake no reviewer is looking for will pass. We found one such gap and closed it by adding the reviewer that reads the whole table; 5 extraction misses stand waived today, each naming its follow-up. We cannot demonstrate that no further gap remains.

The goal is a fully self-contained, automated pipeline — every new trial flowing from raw registry input straight through to finished, structured resource files, end to end and on a schedule, with no manual step.
